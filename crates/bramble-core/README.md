# bramble-core

The Bramble wallet's core: [`wallet-core`](../wallet-core) plus Bramble's own choices, exported
through UniFFI as one library for the browser extension (wasm32, npm
`@starknet-innovation/bramble-core`), iOS (Swift, XCFramework) and Android (Kotlin, JNI).

## What it is

- **Bramble's policy.** The OpenZeppelin account version Bramble deploys (`OZ_ACCOUNT_VERSION`),
  the salt its `KmsPort` defaults to, its multisig coordination policy (`coordination`: the
  `bramble.multisig` identifier, the default relays and "one custom relay replaces them", the page
  cap, the sync window, recipient selection and the sender rule), its portfolio and history
  choices (`PORTFOLIO_POLICY`, `HISTORY_POLICY`), and, under `mobile`, the mobile vault's schema
  and migration chain.
- **Bramble's catalogs.** `catalogs` embeds `generated/` (`networks.json`, `token-registry.json`,
  `accounts.json`, `multisig.json`, rendered by Bramble's `bun run mobile:assets` and copied
  unchanged) and parses each once: the networks and token registry `wallet-core` takes as
  `Catalogs`, the account classes with `resolve_class`, `argent_shape` and `send_authorization`,
  and the pinned multisig class and limits. A file that does not parse fails loudly on first use.
  `tests/catalogs.rs` holds each to its copy under `tests/fixtures/`. The `mobile` feature exports
  them through UniFFI as mobile's core did.
- **The only FFI crate.** UniFFI scaffolding, `CoreError`, `core_info()`, and remote exports of
  `wallet-core`'s records. Functions keep the names and argument order of the extension's
  `KmsPort`. Built as `lib`, `cdylib` and `staticlib`; `uniffi.toml` keeps mobile's module names.
- **The gate on raw keys.** The `raw-keys` feature (default, for the extension) exports the
  functions that take or return a raw Stark private key. The `extension` feature (default, implied
  by `raw-keys`) exports the extension's other KMS and Nostr functions, several of which take or
  return a recovery phrase. Mobile builds `--no-default-features` and gets neither: its phrase
  stays inside `WalletCore`. The one inbound exception is `WalletCore::import_private_key` (P3),
  which takes a pasted key, seals it into the vault and returns only the account's public record;
  no mobile export returns a key (`tests/ffi_surface.rs` checks both directions).
- **The mobile wallet, behind `mobile`.** iOS and Android build
  `--no-default-features --features mobile`: the `WalletCore` object (vault, accounts, send,
  portfolio, history, privacy, multisig coordination), its records and free functions, and the
  mobile-only glue its module exports through (`biometric`, `backup`, `public_store`, the
  wrong-passphrase backoff in `security`), ported unchanged from Bramble's `mobile/core`
  (`docs/PLAN.md`, 2.7). Its modules sit at the crate root, declared in `src/mobile.rs`, which
  `lib.rs` includes, so the Swift and Kotlin names are mobile's. The extension's wasm32 build
  leaves it off. `testing` (implies `mobile`) adds the integration-test hooks; mobile's suite
  needs it (`cargo test -p bramble-core --features mobile,testing`).
- **The mobile vault.** `src/vault_v13.rs` reads and writes the extension's schema v13 inside
  mobile's DEK container (`src/account_store.rs` is the unlocked form; labels, groups, hidden
  accounts and the backup flag are `public_store`'s `preferences.json`). There is no migration: a
  vault an earlier test build wrote is refused once its password is proven, and can be deleted
  (`docs/PLAN.md`, Vault switch).
- **The parity suite.** `tests/parity.rs` holds the core to golden fixtures generated by the
  extension's real code paths; `tests/fixtures.rs` holds those files to the sha256 manifest in
  `tests/fixtures/README.md`. Mobile's regression files (a vault an earlier mobile core wrote,
  and the gift wraps Rust writes for the extension and the iOS UI suite) are in `tests/regression/`.

## What it is NOT

- **Not where wallet logic lives.** Derivation, signing, address computation and Nostr all live in
  `wallet-core`; this crate passes Bramble's constants in and converts types. If it isn't
  Bramble's choice or an FFI concern, it belongs in `wallet-core`.
- **Not a Krusty client.** It never names `krusty_kms`; everything goes through `wallet-core`.
- **Not a generic SDK.** It is on crates.io, but another wallet should depend on `wallet-core`
  directly or add its own `<wallet>-core` crate next to this one.
- **Not the JavaScript package.** The npm entry point and generated TypeScript live in `js/`; this
  crate is the Rust they wrap.
- **Not a source of fixtures.** Files under `tests/fixtures/` are copied unchanged from Bramble and
  never edited to make a test pass.

## Building

```bash
bash tools/check.sh rust                                   # clippy (default, mobile, wasm32) + tests
cargo test -p bramble-core                                 # this crate's tests
cargo test -p bramble-core --features mobile,testing       # with mobile's suite
```

The Swift/Kotlin generator is the `uniffi-bindgen` binary behind the `bindgen` feature.
`AGENTS.md` at the repo root has the rules for changing this crate.

## Live STRK20 smoke

`tests/strk20_live_smoke.rs` runs one STRK20 proof job (`privacy::job::ProofJob`) against a real
discovery service, prover and node (#182). It is `#[ignore]`d, refuses to run when a CI variable is
set, and is run by hand by the owner of a named dev wallet. Its offline twin,
`tests/strk20_live_smoke_offline.rs`, runs the same code over recorded jobs in every test run.

**Warning: Stage A sends the dev wallet's real viewing key to the configured discovery service
and prover.** That is the protocol: whoever runs those services can read the account's private
notes from then on. Use a dev wallet with nothing private worth keeping.

```bash
STRK20_SMOKE_NETWORK=SN_SEPOLIA \
STRK20_SMOKE_POOL=0x… STRK20_SMOKE_DISCOVERY_URL=https://… STRK20_SMOKE_PROVER_URL=https://… \
STRK20_SMOKE_RPC_URL=https://… \
STRK20_SMOKE_MNEMONIC="…" STRK20_SMOKE_ADDRESS=0x… \
STRK20_SMOKE_JOB=register \
STRK20_SMOKE_SEND_VIEWING_KEY="yes, send" \
  cargo test -p bramble-core --features mobile,testing --test integration \
    strk20_live_smoke::stage_a -- --ignored --nocapture
```

Run it once without `STRK20_SMOKE_SEND_VIEWING_KEY` first: every variable is checked and the
hosts that would receive the viewing key are printed, and nothing is sent.

| Variable | Meaning |
| --- | --- |
| `STRK20_SMOKE_NETWORK` | `SN_SEPOLIA`, or `SN_MAIN` with the next variable. No catalog routes Sepolia, so the route below is all yours. |
| `STRK20_SMOKE_MAINNET_ACK` | Required for `SN_MAIN`, exactly `I am using a named dev wallet on mainnet`. |
| `STRK20_SMOKE_POOL` | The privacy pool's address. |
| `STRK20_SMOKE_DISCOVERY_URL` | The discovery service, without `/v1/sync/…`; must pass `config::is_service_url`. |
| `STRK20_SMOKE_PROVER_URL` | The prover; must pass `config::is_service_url`. |
| `STRK20_SMOKE_RPC_URL` | The node, HTTPS only. Printed as its host alone, since a path or query may hold an API key. |
| `STRK20_SMOKE_MNEMONIC` | The dev wallet's phrase. The account key and the pool-scoped viewing key derive from it as the wallet derives them; never printed. |
| `STRK20_SMOKE_ACCOUNT_INDEX` | Account index, default `0`. |
| `STRK20_SMOKE_LADDER` | `account` (default, this wallet's), `address` (Braavos) or `argentx` (Ready). |
| `STRK20_SMOKE_FAMILY` | `openzeppelin` (default) or `argent` (the catalog's default class). |
| `STRK20_SMOKE_ADDRESS` | The account; refused unless it is the address the four variables above derive. |
| `STRK20_SMOKE_JOB` | `register`, `register-deposit` or `deposit`. |
| `STRK20_SMOKE_TOKEN`, `STRK20_SMOKE_AMOUNT` | For a deposit: the token's address and the amount in base units (decimal). |
| `STRK20_SMOKE_SEND_VIEWING_KEY` | Exactly `yes, send`, or nothing is sent. |

What leaves the machine, all through the system `curl` (HTTPS only, no redirects, bodies on stdin,
replies capped at the core's bounds, 30 s per prove attempt):

- to the node: `starknet_blockNumber`, then the pool's nonce (`starknet_getNonce`). Public data.
- to the discovery service: the outgoing walk, and the incoming walk only when the actions spend
  private notes (never for these three jobs), **carrying the viewing key**.
- to the prover: `starknet_proveTransaction` with the `compile_actions` invocation, **carrying
  the viewing key** and the account's signature over the `CallSet` digest (one signature, made
  locally from the phrase).

Stage A ends there and prints each request's purpose, host and path, HTTP status, sizes and
latency, then the outcome: the `apply_actions` call's calldata length and the proof's sizes, or
the exact `ProofRefusal`. No body, key or phrase is printed. Nothing is submitted on chain: Stage B
(sending `apply_actions` with its proof and the fee approval) needs a proof-bearing invoke this core
cannot build yet (P15), and the run ends by saying so.

The proving block is a named simplification. The extension proves at the latest block minus 10,
only once that block is past the scope's previous privacy write and, at that block, the account is
deployed and any deposited balance is visible (`official-sdk-maturity.ts`,
`official-sdk-readiness.ts`). The harness takes the latest block minus 10 with none of those
checks: leave at least 10 blocks after deploying or funding the account and after any earlier
privacy write by it.
